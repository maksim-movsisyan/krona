# Выбираемые данные сетки и дополнительные представления Kokkos

## Размещение файлов

Пути в архиве соответствуют путям в проекте:

| Файл | Назначение |
|---|---|
| `include/krona/execution/types.hpp` | Прежний файл без изменений; приложен для полноты |
| `include/krona/mesh/compute/mesh_view.hpp` | Базовое невладеющее представление и маска групп `MeshData` |
| `include/krona/mesh/compute/mesh_storage.hpp` | Выбор базовых групп, CPU-заимствование или GPU-копии |
| `include/krona/mesh/compute/aux_view.hpp` | Отдельные представления дополнительных связностей и метрик |
| `include/krona/mesh/compute/aux_storage.hpp` | Адаптация подготовленных host-кешей дополнительных данных |
| `include/krona/mesh/compute/detail/array_transfer.hpp` | Общий внутренний механизм attach/upload и проверки размеров |
| `examples/mesh_extensions.cpp` | Пример использования готовых вспомогательных данных в ядре |
| `docs/mesh_compute.md` | Этот документ |

Определение `MeshPart` и существующие `aux_connectivity.hpp`/`aux_geometry.hpp` менять не требуется. `aux_view.hpp` использует объявленные там маски; дополнительные структуры не дублируют их определения. Все новые процедуры header-only. Основной target `krona::mesh_compute` сохраняется. Приложение уже должно иметь обычные зависимости KRONA для mesh/MPI: host-заголовок `aux_geometry.hpp` содержит объявление с `mpi::CommView`, но новые адаптеры сами не вызывают MPI.

## Что именно стало гибче

Основной `MeshView` не содержит всех возможных вспомогательных данных. Есть три независимых представления:

- `MeshView<>`: выбранные базовые массивы `MeshPart`.
- `AuxConnectivityView<>`: выбранные CSR-таблицы из `MeshAuxConnectivity`.
- `AuxGeometryView<>`: выбранные метрики из `MeshAuxGeometry`.

В ядро передаются только используемые представления, группы или отдельные массивы. Добавление нового независимого кеша не требует добавлять его дескрипторы в основной `MeshView`. Дополнительные таблицы существуют в памяти только при явном создании соответствующего host-кеша и его адаптера.

Это расширение доступных данных, а не готовая универсальная реализация численных методов. Распределённый FEM дополнительно потребует нумерации DOF, их владения и обменов. Vertex-neighbour таблицы описывают только ячейки имеющегося локального halo; одна face-neighbour halo-оболочка не гарантирует полноту vertex-neighbour stencil.

## Выбор базовых групп

```cpp
using namespace krona::mesh::compute;

// Прежнее поведение: topology + geometry + halo.
MeshStorage<> usual(host_mesh);

// Прежний shorthand также сохранён.
MeshStorage<> complete(host_mesh, {.with_connectivity = true});

// Только cell-to-node связность и координаты узлов.
MeshStorage<> nodes(host_mesh, {
    .data = MeshData::CellConnectivity | MeshData::NodeCoordinates
});
```

Доступные флаги:

| Флаг | Данные |
|---|---|
| `Topology` | owner/neighbour, патчи и patch CSR |
| `Geometry` | центры, объёмы, нормали и площади |
| `Halo` | индексы pack/unpack |
| `CellConnectivity` | типы ячеек, cell-to-node CSR |
| `FaceConnectivity` | типы граней, локальный номер грани, face-to-node CSR |
| `NodeCoordinates` | координаты узлов |
| `Core` | `Topology | Geometry | Halo` |
| `Connectivity` | три группы узловых данных |
| `All` | все группы |
| `None` | только счётчики |

`with_connectivity=true` добавляет `Connectivity` к `data`; не заменяет маску.

Все локальные счётчики остаются в `view.topology`, даже если `Topology` не выбран. Группировка граней требуется при подключении `Topology`. Полные FVM-метрики не требуются при выборе только connectivity. Проверяются лишь размеры выбранных массивов, основные CSR-границы и допустимость счётчиков. Полная валидация сетки остаётся у host-модуля.

Наличие группы определяется по `view.has(MeshData::...)`, а не по длине одного из массивов. Готовая группа может быть пустой на пустом MPI-ранге.

## Подготовка и подключение вспомогательных данных

```cpp
// Используются существующие host-реализации этих функций.
auto host_conn = krona::mesh::build_aux_connectivity(
    host_mesh, krona::mesh::AuxConnType::CellFaces |
               krona::mesh::AuxConnType::NodeCells);

auto host_geom = krona::mesh::build_aux_geometry(
    host_mesh, krona::mesh::AuxGeomType::FaceCellDistance |
               krona::mesh::AuxGeomType::FaceInterpolationWeights);

krona::mesh::compute::AuxConnectivityStorage<> conn_storage(host_mesh, host_conn);
krona::mesh::compute::AuxGeometryStorage<> geom_storage(host_mesh, host_geom);

const auto conn = conn_storage.view();
const auto geom = geom_storage.view();
```

Без явной маски адаптер подключает все группы из `source.active_mask`. Можно подключить только подмножество:

```cpp
krona::mesh::compute::AuxConnectivityStorage<> only_faces(
    host_mesh, host_conn, krona::mesh::AuxConnType::CellFaces);
```

Если запрошенная группа ещё не подготовлена, конструктор выбрасывает `std::invalid_argument`. Он не запускает её построение скрытно и не вызывает MPI. `WallDistance` можно подключить только после явного успешного построения соответствующего кеша через существующий коллективный API. Маска готовности сохраняется и для корректно построенных пустых массивов.

Проверка количества элементов не доказывает актуальность кеша после переупорядочивания. Все источники должны описывать одну нумерацию и один снимок сетки.

## Доступ к CSR внутри ядер

Имена массивов повторяют host-кеш. Например, `cell_faces_offsets` и `cell_faces` остаются доступны напрямую. Для удобства имеются методы:

- `cell_faces_of(cell)`;
- `cell_neighbors_face_of(cell)`;
- `cell_neighbors_node_of(cell)`;
- `node_cells_of(node)`;
- `node_faces_of(node)`.

Они возвращают небольшой `IndexRow`, содержащий только const-указатель и длину. Это аналог используемого в host-коде `span` для данного интерфейса, с явно аннотированными Kokkos-методами:

```cpp
const auto faces = conn.cell_faces_of(cell);
for (std::size_t i = 0; i < faces.size(); ++i) {
    const auto face = faces(i); // Также работает faces[i].
    // ...
}
```

Методы работают и на host, и в Kokkos-ядрах при доступности соответствующей памяти. Они не выделяют память. Debug-проверки проверяют наличие таблицы и диапазон строки; release-ядро должно получать заранее подготовленные данные. `std::span` не навязывается device-интерфейсу.

## borrows_host и владение

`borrows_host` — `static constexpr`, вычисляемый по точному совпадению `Exec::memory_space` с `Kokkos::HostSpace`. Это не пользовательский runtime-флаг.

- Serial/OpenMP: unmanaged представления ссылаются на исходные векторы. Владеющие дескрипторы `buffers_` существуют, но остаются пустыми и не выделяют массивов. Второй копии элементов нет.
- CUDA/HIP: создаются managed device-буферы только выбранных групп. Host-вектор временно оборачивается без копирования, затем выполняется `deep_copy` в device-буфер. Конструктор ждёт завершения загрузки.

Это одинаково для базовой сетки и обоих дополнительных адаптеров. `view()` копирует дескрипторы, а не массивы. Все kernel views имеют const-элементы. Метрики и поля, которые нужно обновлять, требуют отдельного writable владельца; данный интерфейс представляет подготовленный снимок.

## Время жизни и обновление

На CPU источник `MeshPart` или соответствующий `MeshAux*` должен жить до завершения всех читателей. Нельзя выполнять операции, меняющие адреса или размеры заимствованных векторов. Изменения значений видны без копирования, но должны быть синхронизированы с читателями.

На GPU после завершения загрузки adapter владеет device-копиями. Изменения host-кеша их автоматически не обновляют. Перед изменением сетки/кешей и пересозданием адаптеров завершите использующие старые данные ядра. Независимые хранилища позволяют пересоздать только геометрию или её дополнительные метрики, сохранив топологию.

Топологические изменения и переупорядочивание требуют пересоздать связности, геометрию и представления. Перемещение координат требует обновить геометрию и зависимые метрики; неизменная топология не требует нового connectivity-кеша. Для ALE/AMR это лишь организация данных; алгоритмы обновления, mesh velocity, GCL и расширение halo здесь не реализованы.

Все storages не копируются и не перемещаются. Создание CPU-представлений из временных источников запрещено. Деструкторы не делают скрытого глобального `fence`: завершение работы обеспечивает вызывающий код, до финализации Kokkos.

## Производительность

Проверки масок и выбор загружаемых массивов выполняются при конструировании хранилищ. В обычном ядре нет обязательной проверки backend, виртуального вызова или поиска массива по имени. При `borrows_host=true` ветка выделения/copy отсутствует благодаря `if constexpr`.

Неиспользуемые группы занимают только фиксированные пустые дескрипторы; память под элементы не выделяется. Дополнительные views вообще находятся вне базового `MeshView`. Если захватить все дескрипторы в одно ядро, можно увеличить размер аргументов и давление на ресурсы компилятора/GPU. Захватывайте реально используемые группы и массивы.

Маска не вычисляет недостающие данные. Цена построения вспомогательных связностей/метрик, хранения запрошенных массивов и одноразовой GPU-загрузки остаётся реальной. Гарантии потери не более 5–10% без измерений нет; эта организация данных сама не добавляет обязательной диспетчеризации к каждому доступу.

## Проверка и её границы

Проверено на настоящем Kokkos 5.2.1, C++20/GCC, Serial и OpenMP: прежние сценарии базовой сетки, выбор только узловой связности без FVM-геометрии/группировки, заимствование указателей, выбор подмножеств всех пяти CSR и шести групп метрик, использование row helpers из Kokkos-ядра, отражение host-изменений, пустые ранги/строки CSR и отклонение отсутствующих флагов/неверных размеров.

В стенде использованы присланные `MeshPart` и `MeshAux*` заголовки. Недоступные `raw_mesh.hpp`, generated `config.hpp` и `mpi::CommView` заменены минимальными объявлениями зависимых типов. Адаптеры проверены с заранее подготовленными кешами: реализации host-builder функций из `.cpp` не предоставлены и не тестировались. Стенд не входит в архив.

CUDA/HIP не собраны и не запущены: в окружении нет соответствующих toolchain/GPU. Полный KRONA с MPI/Trilinos здесь также не собран. GPU-путь использует тот же штатный механизм Kokkos View/deep_copy/fence, но требует проверки в окружении проекта.
